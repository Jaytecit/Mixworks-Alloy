# Synesthesia / Alloy resource investigation — 1 November 2026

Alloy has identifiable resource costs worth fixing. Synesthesia's useful model is GPU shader rendering with controlled output resolution and frame delivery. Alloy already uses GPU shaders, but its final frame still travels through CPU memory and the UI. The mixer separately retains substantial decoded/prepared PCM mappings and disk caches. This investigation establishes mechanisms and priorities, not a measured causal attribution of every slowdown or a completed optimisation.

## Why Alloy can consume so much

**Frame delivery:** one 720p BGRA frame is 3.52 MiB; at 60 fps the payload alone is 210.94 MiB/s. At 1080p it is 474.61 MiB/s. These are calculated transport volumes, not retained memory or measured bus traffic. Additional copies, driver synchronisation, UI scheduling and scaling add costs. Merely raising a timer or replacing Python with C++ would not remove this architectural round trip.

**GPU allocation:** prototype `renderer.Target` allocates two textures for every target. The compositor uses only target slot zero. Float passes use RGBA32F (four times RGBA8 storage), and the 512 MiB render-target limit is per pipeline, not a total worker budget. Two pipelines, shared media, compositor and driver allocations need an aggregate budget. Preserve feedback and precision semantics; arbitrary removal of double buffering or float formats would break scenes. No current VRAM measurement was made.

**Audio residency:** `PreparedAudio::residentBytes()` in `Model.h:146` counts only heap samples and excludes mappings. The 1 GiB preparation budget therefore is not a total resident-RAM bound. `PcmStore::read` maps an entire entry, hashes its complete payload and then checks every float for finiteness, touching the whole file before use. `Beatmatch.cpp` can prepare a complete source for a new tempo/pitch, then moves it into mapped storage. This preserves reuse and avoids duplicate heap buffers but can populate many file-backed pages. Project/library owners and up to 100 Undo snapshots can retain audio mappings; shared pointers share backing stores rather than copying every song for every Undo step. The precise owners of today's 100 mappings are not established.

**Disk expansion:** six minutes of stereo 44.1 kHz float PCM occupies about 121.1 MiB, versus 14.4 MB for six minutes at 320 kbps. Additional tempo/pitch/geometry preparations have separate cache keys. This explains a mechanism for growth without asserting that every file is redundant. Reducing the disk quota alone would not cap RAM and may increase repeated preparation.

## Comparison and next implementation boundary

[DJ.Studio's documented storage model](https://help.dj.studio/en/articles/12315405-where-is-the-dj-studio-database-stored-and-how-do-i-free-up-disk-space) references original music since 4.1 and offers cache cleanup. [MixMeister support](https://support.inmusicstore.com/en/support/solutions/articles/69000848901-mixmeister-troubleshooting-mixmeister-crashes-at-launch-or-when-scanning-your-content-library) confirms retained library data and rescanning after removal. Existing Alloy research also records persistent analysis in both products. These sources do not reveal their full decode/residency/presentation algorithms or establish equal-workload resource comparisons. Alloy already retains analysis separately and references original music; it should preserve those strengths.

Recommended order:

1. **Bound mixer residency:** distinguish metadata, decoded PCM, prepared PCM, active mappings and Undo ownership in diagnostics. Keep active/soon-needed playback ready through a bounded read-ahead/preparation working set; release or make inactive audio reacquirable without losing edits, analysis or Undo semantics. Avoid disk faults in the audio callback. Retain integrity validation; investigate safely reusing validation for the same immutable backing object instead of blindly weakening hashes.
2. **Keep live visual output on GPU:** give a dedicated presentation surface access to the completed texture, either in the renderer's own window or via supported shared-texture interop. Send control/audio metadata across the boundary; use a reduced-rate preview or screenshot readback only where needed. Budget both scenes together and reuse buffers. Shared CPU memory would remove socket copies but still leave the GPU readback; it is an intermediate option, not equivalent to direct texture presentation.
3. **Make storage intentional:** expose decoded/prepared cache usage and a suitable adjustable quota; account for fallback roots and temporary files separately. Plan safe retirement of redundant preparations/fallback data while preserving retained analysis, references, current audio owners and all protected evidence. No cleanup is authorised by this report and none was performed.

Acceptance should use the existing five-track/20-minute real-music mix and actual target monitor: delivered frame-gap distribution and missed frames, audio underruns, peak/steady private and resident RAM, mapped PCM and disk growth. Start with one short representative transition when system memory permits; only advance to complete-mix acceptance after it succeeds. No broad stress suite or repeated experimental rebuild cycle by default. The archived incomplete OpenGL refactor is not an implementation ready to restore.

Method discovery consulted [skills.sh software-performance](https://www.skills.sh/vasilyu1983/ai-agents-public/software-performance): attribute the bottleneck and compare under the same conditions. No additional skill or dependency was installed. Question status: GPU/pass methods partially answered; Alloy transfer/cache mechanisms answered by source; current resource scale observed; exact frame-stall cause, Synesthesia swap pacing and competitor memory algorithms unresolved.
