# Plugin latency in the current host

The current finishing configuration supports **active inserts that report zero samples of processing latency**. Full delay compensation for parallel clip/lane paths is not implemented. A creative delay or reverb tail is separate: its echoes do not represent transport latency and do not need to be shifted back onto the source attack.

A plugin that reports nonzero latency remains loaded, editable and savable. Its rack row marks the reported sample count as blocked. Choose the plugin's zero-latency mode, or explicitly bypass/remove the insert before playing, rehearsing or exporting. Mixworks does not silently change bypass or source positions. Session reopening preserves the state and the same restriction.

Playback checks the active insert chains before rendering and checks each processor before/after processing. A reported unsupported change stops transport and clears the affected output block; the main status explains which insert and owner require attention. Export checks before preparation and during rendering, then queries the actual VST3 processor on the UI thread before committing. It rejects unsupported output and keeps the destination. JUCE’s cached value can lag nested native notifications; queue barriers alone do not establish the current native latency. Rehearsal rejects unsupported output rather than publishing a misaligned comparison. Bypassed inserts retain their saved state while allowing the remaining mix to play/export.

This guard follows the latency actually advertised by the native host API. It cannot detect a plugin that reports an incorrect value, or predict a notification before the plugin/host publishes it. Live processing uses the published cache; asynchronous notifications take effect when delivered. Final export admission reads the native value on the required UI thread. Closing cancels/disarms pending admission before joining the worker, so a late callback cannot reference a destroyed renderer. In-process plugin crashes and full latency compensation remain separate unfinished host work.

The local test-only Mixworks Test Latency.vst3 physically delays an impulse by 64 samples and reports exactly that latency, with zero advertised tail. The pre-guard export produced separate impulses at frames0 and64 instead of one combined impulse: retained red evidence is under `.local/latency-25/`. Real fixed/dynamic/bypass/save/reopen/export tests establish the supported restriction; this is not a claim of compensated plugin alignment.
